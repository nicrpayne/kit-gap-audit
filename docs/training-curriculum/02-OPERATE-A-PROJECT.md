# Session 2 — Operate a Project

**Duration:** 45 minutes

## Objectives

Use Audit Change Inbox safely; interpret Scope coverage; capture Decisions without false gates; distinguish Dependencies from semantic relations; route every proposal to its owner.

## Prerequisites

Session 1 complete. Use production for read-only exploration and the stable disposable fixture for acceptance exercises.

## Walkthrough

1. **0–10 min — Audit freshness and inbox.** Read the knowledge state, open Changes, and examine current/proposed, relevance, retrieval, evidence, currentness, and owner.
2. **10–20 min — Govern one fixture change.** Accept a Capability proposal. Observe that Scope changes but execution mapping is not invented.
3. **20–28 min — Scope.** Find mapped capability, **NO EXECUTION WORK MAPPED**, and **NO CAPABILITY YET**. Explain why each affects coverage differently.
4. **28–38 min — Decisions.** Accept/create an open ungated Decision. Demonstrate zero Forecast effect. Inspect Connect to delivery fields without submitting unless the fixture calls for it.
5. **38–45 min — Dependencies.** Select a declared edge and candidate relation; explain why only the former is topology.

## Exercises

- Disposition one fixture proposal each as accepted, deferred, rejected, and information-only; state the effect.
- Trace the accepted capability to its evidence.
- Write a good Decision title with two viable directions.
- For a relation, state the proof needed before declaring dependency.

## Check questions and expected answers

1. **What does Edit in Change Inbox change?** The proposal, not Reality.
2. **What happens when an open Decision is created?** It becomes canonical and unresolved; Forecast does not move unless a DecisionGate exists.
3. **Can an accepted Capability be unmapped?** Yes; product shape and execution mapping are separate.
4. **What is the difference between defer and information-only?** Deferred remains a possible future mutation; information-only is retained context with no owner mutation.
5. **What makes a dependency canonical?** Explicit governed source/target precedence, not semantic relation.

## Common mistakes

Accepting recommended changes without evidence; inventing endpoints to clear completion; gating importance; reading tickets as complete product shape.

## Hands-on task

Starting from the fixture's Change Inbox, govern one capability and one open Decision, verify their distinct owner outcomes, and narrate every non-effect.
