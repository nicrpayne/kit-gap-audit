# Search, Trace, and Inspector

## 1. Purpose

**Question:** Where is the object, what exactly is it, and where did its claim come from?

## 2. Why it is powerful

These three controls make a dense project world explainable without flattening it into a list. Search finds; Inspector reads; Trace isolates a meaningful path.

## 3. Mental model

Use them as a sequence: **query → select → inspect → trace → return to world**. Search match is discovery, Inspector is object detail, and Trace is a focused topology/provenance view. None alone proves causality.

## 4. Truth / ownership boundary

They own view state only. The selected object retains its canonical owner. Inferred edges stay inferred; evidence passages stay evidence; owner links are doors, not mutations.

## 5. Inputs

Audit search index across canonical objects, Findings, intelligence, evidence passages, sources, work, requirements, people, features, checkpoints, and relationships.

## 6. Outputs

Selection, camera focus/cluster expansion, Inspector details, and an isolated path with provenance. No owner state changes.

## 7. Screen tour

| Control | Meaning |
|---|---|
| Query field | Text search across indexed labels/content/basis |
| Match basis | Why a result matched; do not treat rank as confidence |
| Result list | Kind, label, state/currentness where available |
| Fly to | Expands required cluster and moves camera to selected object |
| Selected object card | Short identity and primary action/door |
| Inspector | Type, lifecycle/state, owner, source, grounding, details, connections |
| Trace | Shows only the path relevant to selected object and relation |
| Evidence drill-down | Quote/passage/source chain |
| Clear/close | Restores whole world; traced-out objects were not deleted |

## 8. Primary happy path

1. Enter a specific concept, ticket, person, Decision, or phrase.
2. Read the result kind and match basis.
3. Select; verify the field expands/focuses the real node.
4. Read Inspector before acting.
5. Trace provenance or a declared relation.
6. Open exact evidence/source where available.
7. Follow the owner door if governance is required.
8. Clear Trace and selection.

## 9. Secondary journeys

- Trace source → passage → Finding → Reality.
- Select a Person and confirm that other commitments are context, not person→work topology.
- Search a Requirement and verify structural source role rather than keyword inference.

## 10. Writes / side effects

None. Search, selection, camera, expanded cluster, and Trace are reversible view state.

## 11. What it does not do

Search does not accept a claim. Trace does not convert an inferred relation into a Dependency. Inspector does not certify source correctness or freshness.

## 12. Warnings / empty states

No result may mean the object is outside the package/index, not nonexistent. “No grounded implementation link” is not “not implemented.” Uncited/derivative/stale states require source judgment.

## 13. Handoffs

Audit Change Inbox for proposals; Scope/Decisions/Dependencies/Capacity/Timeline for ownership; upstream KE/Hermes for missing evidence.

## 14. Common mistakes

Searching broad words and treating top rank as truth; leaving Trace active; mistaking related edge for precedence; assuming a person node proves task assignment.

## 15. Troubleshooting

If result exists but cannot be seen, use fly-to/fit; auto-expansion should reveal it. If the Inspector and node label disagree, capture both. If a provenance chain ends at derivative wiki only, seek the raw source.

## 16. Operator checklist

- [ ] Result kind and match basis read
- [ ] Selected project correct
- [ ] Owner and currentness understood
- [ ] Evidence chain inspected
- [ ] Trace cleared before broad reading

## 17. Real example

Search “Offline Capture,” select the accepted capability, inspect its execution mappings, then Trace to the evidence passage. The capability can be Reality even if one supporting wiki page is derivative; the provenance tells you how much trust to place in that support.
