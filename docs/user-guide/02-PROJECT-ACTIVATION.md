# Project Activation

## 1. Purpose

**Question:** How do I reconstruct dormant project knowledge and establish the first governed Reality without pretending the knowledge is already true?

## 2. Why it is powerful

Activation makes starting a project rigorous: identity and evidence exist before Scope, candidates remain reviewable, the manifest shows the exact canonical boundary, and the first Audit exposes what was intentionally not invented.

## 3. Mental model

`Pre-Reality identity → scan → immutable package → Bootstrap Review → Activation Manifest → atomic activation → First Audit.`

“Accept” during review means “include in the manifest.” Only **ACTIVATE PROJECT** crosses into Reality.

## 4. Truth / ownership boundary

ProjectBootstrap owns pre-Reality identity, packages, candidates, dispositions, and review revision. Activation atomically creates the Scope identity and accepted canonical objects. It never turns person mentions, semantic relations, or capabilities into staffing, dependencies, or execution links by implication.

## 5. Inputs

Canonical name, aliases, owner/source hints, Signal-held knowledge and/or a companion-produced bounded bootstrap package containing artifacts, evidence passages, current intelligence heads, typed relations, proposals, gaps, and ambiguities.

## 6. Outputs

One activated Scope; aliases; accepted Capabilities/Decisions/Dependencies/Sources where valid; ContextSnapshot 01; first Audit/Findings; ProjectActivation record; preserved review ledger. Exact output depends on accepted candidates and validation.

## 7. Screen tour

| Area | Meaning |
|---|---|
| Add project | Canonical identity, aliases, owner hint, source hints |
| Search existing knowledge | Uses Signal-held knowledge; does not grant Railway local corpus access |
| Create & scan | Creates pre-Reality identity and starts discovery |
| Scan pipeline | Queued/running/stage/completion status |
| Provider coverage/gaps | Which sources/retrieval modes were usable; PARTIAL PACKAGE stays explicit |
| Enter Review | Opens candidate governance after a package exists |
| Section rail | Capabilities, Decisions, Dependencies, Sources, Missing information, Ambiguities; counts and pending counts |
| Candidate card | Kind, state, changed flag, operator assertion, title, rationale, fingerprint, currentness, execution-link warning |
| Provenance Inspector | Evidence vs derived passages, quote, source, independence, attach/detach |
| Accept / Defer / Reject / Information only | Review disposition, still NOT REALITY |
| Add manually | Operator assertion retained as such |
| Activation Manifest | Canonical vs external/candidate columns, gaps, blockers, revision |
| ACTIVATE PROJECT | Consequential atomic boundary |
| First Audit | Newly governed Reality plus execution/provider/ambiguity gaps |

## 8. Primary happy path

1. Create identity with meaningful aliases.
2. Scan and wait for a completed package.
3. Review every section; use provenance before disposition.
4. Accept only candidates that should be canonical on day one.
5. Keep derivative-only, ambiguous, unsupported, or not-yet-ready items deferred/information-only.
6. Open the manifest and read both columns aloud.
7. Acknowledge unresolved gaps only when understood.
8. Activate in the intended environment.
9. Read First Audit and configure the missing owner truth.

## 9. Secondary journeys

- **Start blank:** create identity without searching, then add/govern manually.
- **Rescan:** produces a new immutable package/revision; it does not mutate accepted candidates silently.
- **Retry activation:** idempotent activation converges on the original record after response loss.

## 10. Writes / side effects

Create & scan writes only pre-Reality records. Candidate dispositions write the review ledger. Activation runs serializably and creates the governed initial state atomically; validation failure rolls back all writes.

## 11. What it does not do

No ticket mapping, DecisionGate, person/allocation, milestone, or certification of provider completeness is implied. “Capability accepted” does not mean “executable.”

## 12. Warnings / empty states

- **NOT REALITY:** expected throughout review.
- **PARTIAL PACKAGE:** inspect missing providers before activation.
- **DERIVATIVE ONLY:** seek raw support for consequential claims.
- **execution link missing:** expected for a newly accepted capability.
- **Forecast Unavailable after activation:** expected until reliable execution mapping exists.

## 13. Handoffs

First Audit → Scope mapping → Decisions/Dependencies → Capacity → Forecast → Timeline → readiness.

## 14. Common mistakes

Confusing candidate acceptance with activation; using aliases as separate projects; promoting semantic relations to dependencies; assuming a green provider means complete discovery.

## 15. Troubleshooting

If scan cannot start, check companion identity/heartbeat and ingestion completion. If activation is disabled, inspect manifest blockers and review revision. Never fix uncertainty by inventing required endpoints.

## 16. Operator checklist

- [ ] Identity and aliases are unambiguous
- [ ] Package completed and provider gaps understood
- [ ] Every candidate dispositioned
- [ ] Provenance inspected for accepted material
- [ ] Manifest canonical/external split confirmed
- [ ] First Audit reviewed

## 17. Real example

The disposable Harbor Relay proof accepted one capability, one open Decision, and one raw transcript; deferred a dependency and kept a derivative wiki source information-only. Activation created zero work links, gates, people, allocations, or milestones, so Forecast honestly remained unavailable.
