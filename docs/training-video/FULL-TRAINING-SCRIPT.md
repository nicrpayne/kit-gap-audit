# Full Signal Training Script

**Recommended finished runtime:** 31–35 minutes. The spoken copy is intentionally complete; pauses for interaction and inspection account for the range.

Use the disposable demo fixture described in `DEMO-STATE.md`. Put `DISPOSABLE FIXTURE · production code 6c46ce9` on the opening slate and any shot containing fixture data.

## Chapter 1 — Cold open

**Estimated duration:** 1:15  
**Screen:** Master Control Room, Reality baseline.  
**Cursor:** Rest for the first sentence; then move across the five telemetry readings.  
**Zoom/callout:** Numbers 1–5: Reality, Choices, Capacity, Outcome, Time.  
**Visual asset:** Signal at a Glance appears for five seconds.

**Narration:**

“A project rarely fails because nobody had information. More often, the information was everywhere: in a transcript, a wiki page, a design, a ticket, somebody’s memory, and a decision that everyone thought somebody else had made. The difficult question is not, ‘what have we heard?’ It is, ‘what do we currently accept as true about delivery, what is still unresolved, and what follows from that?’

This is Signal. Signal is a governed delivery instrument. It sits between a second brain that can understand the project and the human responsibility to decide what the project actually is. Once those facts are governed, the consequences can update automatically. I can ask what happens if a person moves, a capability leaves the release, or a serial decision resolves—and I can see the answer without turning the hypothetical into Reality.

The rule underneath everything you are about to see is simple: changing Reality is governed; calculating consequences is automatic.”

**Transition:** Select the project name, then release it without changing. “To understand why that separation matters, start with the information problem.”  
**Fallback if live data differs:** “The values in this project move; the five questions and ownership boundaries do not.”

## Chapter 2 — The problem

**Estimated duration:** 2:00  
**Screen:** Static human-architecture visual, then a Control Room source/currentness detail.  
**Cursor:** Trace the chain from source to Reality.  
**Zoom/callout:** Highlight “Evidence ≠ Reality.”

**Narration:**

“Linear is excellent at telling me which executable work exists and where it is in a workflow. But it cannot tell me the whole accepted product shape when a capability has no ticket, whether an organizational choice has actually been made, or whether two projects merely sound related or one truly waits for the other.

A wiki is excellent institutional memory. But a wiki page is usually synthesis. It can be thoughtful and current and still be derivative. It should not silently become a staffing plan, a dependency, or a promise.

Hermes changes the equation because it can read longitudinally. It can connect a meeting today with a design note from last month, surface contradictions, and prepare structured intelligence. That is powerful precisely because Signal does not grant it authority. Hermes owns what was said and understood. Signal owns what is accepted as true about delivery.

That boundary gives us three honest verbs. Knowledge proposes. A human governs. The model calculates. If the source changes, Audit can tell me. If I accept the implication in the appropriate owner instrument, Forecast can show the consequence. No tool gets to skip the middle step.”

**Transition:** Move to the Signal at a Glance visual. “Here is the complete loop.”  
**Fallback:** If source age is unavailable, point to the owner label and say, “The absence is itself part of the trust story.”

## Chapter 3 — The second brain and operating loop

**Estimated duration:** 2:15  
**Screen:** `00-signal-at-a-glance.svg`, then Audit knowledge widget.  
**Cursor:** Follow Knowledge → Audit → Govern → Model → Forecast → Communicate.  
**Zoom/callout:** Pause at the governance column.

**Narration:**

“Meetings, correspondence, plans, and source documents enter the knowledge environment. KE compiles institutional memory. Hermes ingests and reasons over that history. Signal does not copy the whole corpus. It receives a bounded, source-aware project package and asks a narrower question: does this current intelligence disagree with accepted delivery Reality?

Audit is the daily hinge. It checks whether the latest completed package and the frozen Signal snapshot agree. If Hermes is still ingesting, Signal waits. If the local companion is offline, Signal says so. If new completed intelligence exists, Signal can refresh and produce Changes since last Audit.

Those changes are proposals with an owner. A capability belongs to Scope. A choice belongs to Decisions. Precedence belongs to Dependencies. People and allocations belong to Capacity. Planned time belongs to Timeline. The operator accepts, defers, rejects, marks information-only, or completes missing owner detail.

Only then do we model. A Scenario is a disposable overlay. Forecast calculates likely outcome, range, and target confidence. The Control Room composes the current picture. Reports freeze the right story for an audience. When supported, an interactive Site receives an explicit handoff; Signal never silently publishes.”

**Transition:** Dissolve back to Control Room. “Now we can read the room correctly.”  
**Fallback:** If freshness is not Current, name the displayed state verbatim and continue without refreshing production.

## Chapter 4 — Master Control Room

**Estimated duration:** 2:40  
**Screen:** Control Room, Command View.  
**Cursor:** Project label → Live now → Timeline span → last saved report → telemetry → selected project/gate → Inspector.  
**Zoom/callout:** Likely, target, confidence, commitment, coverage/currentness.

**Narration:**

“The Master Control Room answers one question: what deserves attention right now? It owns none of the facts on screen. That is a feature, not a limitation. Every important reading has a door back to the instrument that owns it.

At the top, I can verify the live time reference, the Timeline span, and when the last forecast-bearing report was saved. A saved report is historical; it is not the live Forecast. The Views control changes which tools are on the desk, not the project. Add event opens Timeline because Timeline owns events.

The operating sequence is numbered. Reality tells me what the project currently accepts. Choices tells me what is open and how many choices actually gate delivery. Capacity tells me whether the team is named and reconciled or still an aggregate basis. Outcome tells me the likely landing and uncertainty. Time tells me what is planned, projected, committed, or already occurred.

When I select this gate, the Inspector changes the question I am asking. Nothing canonical changes. I can follow its owner link to Decisions, change nothing, and return. If the forecast ever refuses because a dependency cycle or required read is broken, the Control Room stops instead of showing plausible-looking numbers. Trust is more important than filling the page.”

**Transition:** Click Audit. “The Control Room points; Audit tells me what changed outside the model.”  
**Fallback:** If the fixture opens another View, say, “Views are local presentation; I’m choosing Command for the complete tour,” and select it.

## Chapter 5 — Audit: the daily entry point

**Estimated duration:** 3:20  
**Screen:** Audit world, knowledge widget, Change Inbox, Source Health, Readiness.  
**Cursor:** Reality center → Project Model → Project World → Attention/Open Loops → Sources → widget → inbox proposal → evidence.  
**Zoom/callout:** Current accepted versus Proposed.

**Narration:**

“Audit asks where accepted Reality disagrees with evidence and execution around it. The center is accepted Reality. Around it are project structure, execution, source artifacts, evidence passages, intelligence, people, decisions, dependencies, and Findings. Shape says what kind of object this is. Color says its state. Position can show category or disagreement; it is not a confidence score.

The knowledge control is my daily starting point. Current means the latest completed package and frozen snapshot agree. It does not mean every source is complete or every claim is right. New intelligence available means I can refresh. Ingestion in progress means wait. Companion offline means the local bridge must come back; Railway cannot read my local corpus.

In Changes since last Audit, every proposal shows its named owner, current state, proposed state, project relevance, retrieval basis, exact evidence, currentness, and expected consequence. I can edit the proposal without changing Reality. I can defer it, reject it while preserving provenance, or keep it information-only.

Accept is never generic. This capability proposal belongs to Scope. In the fixture, I accept it there. The notice tells me the owning instrument changed and derived reads refreshed. The evidence did not become infallible. The accepted capability did not receive a ticket by magic. Audit discovers; owner instruments govern.

Source Health tells me which providers are configured and current. Report Readiness turns missing execution, stale knowledge, unreconciled capacity, or incomplete Forecast into named blocker doors.”

**Transition:** Open the accepted capability in Scope. “Now we see exactly what acceptance did—and what it refused to do.”  
**Fallback:** If the production inbox is empty, use the labeled fixture screenshot and say, “Production has no safe pending proposal to mutate, so this governed action is shown in the disposable fixture.”

## Chapter 6 — Scope: what are we shipping?

**Estimated duration:** 2:35  
**Screen:** Scope fixture with mapped, unmapped, no-capability, out-of-release.  
**Cursor:** Coverage summary → mapped module → unmapped module → NO CAPABILITY YET → open shape Decision → floor.  
**Zoom/callout:** Distribution low/likely/high and Reality ghost.

**Narration:**

“Scope owns product shape. That sounds obvious until the work tracker and the product model disagree. Here, one accepted capability is mapped to executable work. Another accepted capability shows NO EXECUTION WORK MAPPED. And one execution item shows NO CAPABILITY YET.

Those are different gaps. The first says we have accepted product intent but cannot yet see current work representing it. The second says executable work exists without an accepted product-shape container. Signal refuses to solve either by pretending tickets and capabilities are the same thing.

Each capability has a three-point modeled distribution. The horizontal span is low to high. The likely value has its own locator. A taller peak means a more concentrated estimate, not more work. During a Scenario, the active curve moves while Reality remains as a dashed ghost.

I can remove or re-estimate a capability in Scenario to ask what would change. A removed capability leaves a vacated seat because Reality has not disappeared. If the release is dominated by a DecisionGate or dependency floor, cutting Scope may not move the date. That is a useful answer.

Open shape Decisions are read-only here because Decisions owns them. Capacity and Forecast are also doors. Scope says what is in the product; it does not choose for the organization, staff the team, or promise the landing.”

**Transition:** Follow the open shape Decision. “A product boundary can remain uncertain without becoming fake schedule delay.”  
**Fallback:** If labels differ, name the visible coverage reason exactly and preserve the mapped/unmapped distinction.

## Chapter 7 — Decisions: making tension operable

**Estimated duration:** 2:40  
**Screen:** Decisions circuit with candidate, open ungated, gated, decided.  
**Cursor:** Open lane → ungated Decision → gate connection → gate detail → Assume resolved → Back to Reality.  
**Zoom/callout:** “Decision ≠ Gate.”

**Narration:**

“A Decision is a choice. A DecisionGate is the much narrower claim that a target Scope literally waits in series for that choice to resolve. Signal separates them because writing down an important question should not silently move every date.

This open Decision is real and ungated. It can have an owner, needed-by date, options, context, and evidence. It has zero Forecast effect. That does not make it unimportant. It means delivery can proceed in parallel, or we do not have enough evidence to claim otherwise.

This second Decision has an explicit gate. Connecting it required four answers: what Scope waits, why it cannot proceed, what evidence supports that claim, and how long resolution could take in low, likely, and high cases. Only this structure touches the delivery circuit.

The current engine treats gate time as strictly serial. Two gates add. If two questions can resolve in the same week, modeling both as independent serial waits would exaggerate delay.

I can select Assume resolved in Scenario. The wall releases and Forecast recalculates, but the Decision remains open in Reality. Back to Reality restores the gate. When the organization chooses, I record the chosen option and rationale in Decisions. Scenario never decides for us.”

**Transition:** Open Dependencies. “Choices can block work, but projects can also wait on other projects.”  
**Fallback:** If no gate is available, use the fixture's Approve the iTrack handoff Decision and state its labeled 1/4/10-day variant.

## Chapter 8 — Dependencies: what waits on what?

**Estimated duration:** 1:55  
**Screen:** Dependencies/Orbit with Platform and iTrack/JSA edge.  
**Cursor:** Focus project → declared edge → candidate relation → Inspector semantics → Scenario cut.  
**Zoom/callout:** Direction arrow and coverage warning.

**Narration:**

“Dependencies owns explicit project precedence: this project cannot land before that one. The production navigation calls this Dependencies; the current surface title says Orbit. That naming mismatch is logged, but the ownership rule is clear.

Here the focused project has a declared upstream relationship. I select the edge and read its direction and provenance. Forecast can propagate the upstream landing into the downstream result. It also propagates uncertainty and coverage: if the upstream project's execution model is incomplete, the downstream project cannot inherit a canonical full-project forecast.

A candidate relation can appear nearby, but it remains a proposal. Two concepts being related, appearing in the same meeting, sharing a person, or occurring next to each other in time does not prove precedence.

I can cut the edge in Scenario to understand leverage. That does not delete it. If the date changes, I have learned the modeled cost of the declared dependency. If it does not, another constraint is dominant. The next question is evidence, not how to force movement.”

## Chapter 9 — Capacity: the team is part of the model

**Estimated duration:** 3:00  
**Screen:** Portfolio mixer, aggregate warning, Set actual team drawer, named exact state, Scenario.  
**Cursor:** Forecast basis → roster → split allocation → raw/effective → fader → Scenario Inspector → Discard.  
**Zoom/callout:** 0.50 raw → 0.45 effective.

**Narration:**

“Capacity is not headcount. It is a governed picture of who is available, how that availability is split across projects, and the shared cost Signal applies when people switch contexts.

An older project may show aggregate unreconciled capacity. Forecast can remain operational on that legacy basis, but Signal must not claim a named team. Set actual team asks for the complete roster, each person's available FTE, and their allocation across every tracked project. It catches duplicate people, unknown projects, invalid FTE, duplicate project rows, and over-allocation. The final confirmation is deliberately strong: this is the complete roster, and named allocations become authoritative.

In this fixture, Person A has one FTE split equally between JSA and iTrack. Each project receives point-five raw FTE. With a ten-percent switching cost, each receives point-four-five effective FTE. That number is a model input, not a productivity score, and it says nothing about which ticket the person is working on.

Now I ask a real question: what if this allocation moves toward iTrack? The Scenario bar turns violet and the Inspector shows the input delta and affected outcomes. A faster iTrack direct path may be offset if Platform slows and iTrack waits on it. The portfolio answer is systemic.

I discard. I would commit only if this Scenario were the intended actual roster and allocation state—not because the room liked the date.”

**Transition:** Open Forecast. “Now we can read the consequence without confusing it with the input.”  
**Fallback:** If production capacity is aggregate, keep it read-only and use the fixture for named reconciliation.

## Chapter 10 — Forecast: consequences, not guesses

**Estimated duration:** 3:00  
**Screen:** Forecast canonical state, then modeled-subset fixture.  
**Cursor:** Coverage → currentness → body → likely → window → target → confidence → macros → Reality comparison.  
**Zoom/callout:** Coverage before date.

**Narration:**

“Forecast answers where we are likely to land, within what window, and why. But the first thing I read is not the date. It is coverage.

Forecastable means the execution source is reliable, accepted capabilities are represented in current work, no product-shape Decision remains open, and the dependency closure is covered. Modeled subset means the math ran for the inputs it has, but those inputs do not represent the full accepted project. Unavailable means Signal has no reliable execution input to model.

The fixture proves why this matters. The engine can produce a precise iTrack result: September twenty-first, with a September twentieth to twenty-second window and one hundred percent raw confidence against the October thirty-first target. But iTrack has zero own execution items and four open shape Decisions. Signal must not expose that as a canonical project forecast. Precision is not coverage.

On a covered project, the solid body shows the active distribution. The center is the likely date. The outer span communicates uncertainty. The target line asks what fraction of these same runs lands on time. If I move the target seven days, the confidence changes; the body does not. Target is evaluation, not a forecast input.

Macros show work, serial gates, people/capacity, and what the model knows. In Scenario, Reality remains as a dashed ghost so I can say exactly what moved and what did not.”

**Transition:** Open Timeline. “Forecast tells us where we land now; Timeline remembers what we believed then.”  
**Fallback:** If the current project is incomplete, use it as the lesson and do not narrate its date as canonical.

## Chapter 11 — Timeline: the project in time

**Estimated duration:** 2:10  
**Screen:** Timeline at start, playback, NOW, selected event.  
**Cursor:** Play → historical report step → NOW → live Forecast → planned milestone → Inspector.  
**Zoom/callout:** planned / projected / committed / occurred.

**Narration:**

“Timeline owns the project's relationship with time. It places plan objects, Decisions, execution, historical Reports, the live Forecast, targets, and commitments on one axis—but it keeps their semantics separate.

When I press Play, the project story unfolds. Historical forecast memory comes only from reports we actually saved. Between two reports, the remembered date holds. When the next report is crossed, it steps. Signal never reruns today's engine for a date in the past, because that would manufacture a belief nobody held.

At NOW, the story hands off to the live Forecast and its currentness. A planned milestone is not the projected landing. A target is not a commitment. An occurred event has an actual historical date.

Only TimelineEvent rows can be moved or deleted here. A Forecast mark belongs to Forecast. A Report belongs to history. A Decision belongs to Decisions. A Linear item belongs to execution. The Inspector tells me the owner before it offers an action.

And one more discipline: if a Decision was settled the day before a report moved, Timeline may show adjacency. It does not claim causality unless the frozen report itself supports it.”

**Transition:** Return to Audit readiness, then Reports. “Once the live state is trustworthy, we can communicate it.”  
**Fallback:** If there is no report history, say, “There is no historical belief to replay; Signal does not invent one.”

## Chapter 12 — Reports: mixing the story

**Estimated duration:** 2:50  
**Screen:** Readiness, Reports composer, finished brief, history, Site handoff preview.  
**Cursor:** Readiness blockers → audience → purpose → module rack → operator note → create → history provenance.  
**Zoom/callout:** same facts, different lens.

**Narration:**

“I do not start in Reports. I start with Report Readiness. Signal checks execution coverage, accepted Scope, capacity reconciliation, source health, and Forecast. If something is missing, the blocker is a door to the owner. Readiness does not promise the future; it says the defined checks pass now.

In the composer, I choose who this is for and why. Delivery Leadership plus Weekly Update is the flagship recipe. It leads with outcome, commitment, movement, why this date, acceleration levers, promoted leadership asks, what changed, what comes next, dependencies, source health, and caveats.

An Executive recipe is shorter. A Portfolio/Staffing recipe emphasizes capacity and tradeoffs. The underlying owner facts do not change. I can reorder modules or change their density. I can add an operator note, but it stays clearly labeled as authored context. Candidate asks never become leadership asks unless I promote them.

When I create the report, Signal stores an immutable snapshot and its recipe. I re-open it from history and verify generated time, Reality or Scenario mode, source currentness, likely, target, commitment, and caveats. If live Reality changes tomorrow, this report remains what we said today.

The interactive Site path is a handoff bundle, not automatic publishing. A human remains in the loop at the communication boundary too.”

**Transition:** Open Add project. “The same governance starts before a project even has Scope.”  
**Fallback:** If Reports is not ready, demonstrate the blocker honestly and use the deterministic Report fixture for creation.

## Chapter 13 — Project Activation

**Estimated duration:** 2:50  
**Screen:** Add Project, scan, Bootstrap Review, provenance, manifest, First Audit.  
**Cursor:** identity → pipeline → sections → candidate → evidence → manifest columns → activation boundary → First Audit.  
**Zoom/callout:** NOT REALITY; WILL BECOME CANONICAL / WILL REMAIN EXTERNAL.

**Narration:**

“Project Activation is how Signal starts with dormant knowledge without pretending the reconstruction is truth. I create a pre-Reality identity with a canonical name, aliases, and hints. Create and scan does not create Scope, Forecast work, staffing, Decisions, Dependencies, milestones, or Reality.

The local companion reconstructs bounded project knowledge and posts a package. The scan shows provider coverage and gaps. A partial package can still be reviewed, but it remains partial.

Bootstrap Review separates Capabilities, Decisions, Dependencies, Sources, missing information, and ambiguities. Each candidate carries a fingerprint, currentness, and evidence. A derivative wiki passage is labeled derivative; it is not a second independent source. Accept here means include in the future manifest. The screen says NOT REALITY because nothing canonical has been written.

The Activation Manifest is the point of no ambiguity. One column says what will become canonical. The other says what will remain external or candidate. In the Harbor Relay fixture, the operator accepts one capability, one Decision, and one raw transcript; defers the dependency; and keeps the derivative wiki information-only.

Activation is atomic. It creates the initial Scope, accepted objects, source registration, ContextSnapshot zero-one, first Audit, and activation record. It creates zero work links, gates, people, allocations, or milestones by implication. The First Audit makes those missing truths visible, so the next step is Scope—not a fabricated green forecast.”

**Transition:** Return to the full-loop visual. “We have now crossed every boundary in the system.”  
**Fallback:** Never activate production for the recording. If the disposable companion is unavailable, use the labeled fixture sequence screenshots.

## Chapter 14 — The full loop

**Estimated duration:** 1:45  
**Screen:** End-to-end table/Signal at a Glance, then quick cuts across instruments.  
**Cursor:** One pass along the arrows.  
**Zoom/callout:** proposal → owner write → automatic consequence → immutable story.

**Narration:**

“Here is the complete operating loop in one example. A meeting reveals a capability and an unresolved organizational tension. The source enters KE. Hermes updates the structured understanding. Audit notices new completed intelligence and proposes a Scope change plus a Decision.

I accept the capability into Scope. It remains unmapped until real executable work represents it. I accept the choice into Decisions. It remains open and ungated, so no date moves. I establish the complete named team in Capacity. I declare a dependency only when precedence is explicit. I connect a DecisionGate only when work truly waits in series.

Forecast recomputes. Timeline updates the live projection while preserving what historical reports said. The Control Room composes the new operating picture. Report Readiness tells me whether the story is safe to communicate. Reports freezes the appropriate audience lens.

At every step I can answer six questions: what did I see, what did I do, which canonical owner changed, what did not change, what recalculated, and why the next instrument follows. That is how Signal stays explainable.”

**Transition:** Control Room with a Scenario change. “The practical benefit shows up in a real conversation.”  
**Fallback:** Use the annotated operating-loop asset if any live route is unavailable.

## Chapter 15 — What this changes for my work

**Estimated duration:** 2:00  
**Screen:** Control Room/Portfolio Scenario and Inspector.  
**Cursor:** One capacity move, inspect changed and unchanged outcomes, discard.  
**Zoom/callout:** question → consequence → why.

**Narration:**

“The most important change is not that Signal gives me more information. It changes the quality of the questions I can ask and answer.

Before a meeting, I can see whether the knowledge package is current, what changed, which choices remain open, whether the team picture is named or aggregate, and whether the forecast covers the accepted product. I walk in knowing where uncertainty really lives.

During a meeting, I can play the project. If someone asks what happens when James moves to iTrack, I change one Scenario input. I can show the direct effect, the dependency effect, and the project that did not move because another constraint dominates. Then I can inspect why and return to Reality. We do not have to confuse an interesting idea with a staffing decision.

After the meeting, I can put new evidence upstream, govern the implications deliberately, and create a brief whose claims have owners, sources, ages, and caveats. Contradictions do not have to become vague risk language; they can become open Decisions with viable directions. Schedule pressure does not have to turn the target into the forecast.

For me as a product and delivery leader, that means better preparation, cleaner decisions, more honest uncertainty, and communication that can survive the question, ‘wait—why?’”

**Transition:** Discard Scenario; hold on Reality. “That brings us back to the rule we started with.”  
**Fallback:** If no named person is safe to show, say “one developer” and use fixture labels.

## Chapter 16 — Close

**Estimated duration:** 1:10  
**Screen:** Reality baseline, then Signal at a Glance end card.  
**Cursor:** None after returning to Reality.  
**Zoom/callout:** final two laws.

**Narration:**

“Signal is not trying to replace the knowledge system, the task tracker, or human judgment. It gives each one a precise role.

The knowledge system remembers and reasons. Audit discovers disagreement. Owner instruments govern product shape, choices, dependencies, people, and time. Scenario lets us ask safely. Forecast calculates consequence. The Control Room helps us operate. Reports helps us communicate without rewriting history.

The strongest version of this product is not the one that automates the most decisions. It is the one that makes the boundary between evidence, judgment, and consequence unmistakable—then makes the consequence fast enough to use in a real conversation.

Changing Reality is governed. Calculating consequences is automatic. Audit discovers. Owner instruments govern. Likely is not target, and neither one is a commitment. That is how I play the project without pretending the project is simpler than it is.”

**Transition:** End card: “Signal · governed delivery truth.”  
**Fallback:** None; this close is data-independent.
